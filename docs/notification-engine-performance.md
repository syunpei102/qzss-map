# 通知エンジン高速化の検証

2026年11月8日（日）．

## 対象と設計

- 対象は受信機から`/ingest`へ届いた電文を，ブラウザ購読先のWeb Pushサービスへ依頼するまでのサーバー処理．端末への配達時間は携帯網，OS，Web Pushサービスの状態にも左右される．
- アクティブ通報の同期ファイル保存と詳細ログを通知依頼の後へ移した．Cloud Run側のローカル控えは順序を保った非同期保存とし，ラズパイのローカル専用運用は従来の同期保存を維持した．
- 地域別通知の通知済み記録をまとめて更新し，地域の件数だけ期限切れトークンを走査していた処理を1回にした．
- 緊急地震速報，地震・震度，津波，JアラートはWeb Pushの`high`優先度を使う．古い警報が後日届かないよう種別に応じてTTLを制限した．
- 複数の購読先への送信は並行開始する．一時的なHTTPエラーや接続エラーを受けた購読先だけ短いジッターを置いて1回再試行する．全購読先が一時的に失敗した場合は503を返し，受信機側の既存の再送キューにつなぐ．
- Cloud Runのリクエスト課金では応答後のCPUが制限されるため，Web Pushサービスの受理まで`/ingest`のリクエストを維持する．停止時は進行中の送信と状態保存を待つ．

## 測定

`node scripts/benchmark-notification-dispatch.js`で旧版と新版を各500回計測．通報の更新と期限切れ処理は本番と同じ`report-state.js`を使用し，アクティブ通報41件，保存JSON約104KB，購読先1件を模擬した．Web Pushライブラリ以降の通信はモックとし，通報処理開始から`sendNotification`の呼び出しまでを測った．同一のMacで3回ずつ実行した中央値は次のとおり．

| 実行 | 旧版 | 新版 |
| --- | ---: | ---: |
| 1 | 0.184ms | 0.029ms |
| 2 | 0.186ms | 0.030ms |
| 3 | 0.192ms | 0.031ms |

中央値の代表値で約84%短縮し，目標の半減をサーバー内の通知開始処理について達成した．Web Push事業者の応答や端末表示までの時間が半分になったことを示す測定ではない．

`npm test`で126件が成功．ローカルサーバーでは`GET /`が200，認証付き`POST /ingest`が204だった．

## 運用上の制約

- Web Pushの受理はスマホへの表示完了を意味しない．OSの省電力設定や通信断を含む1秒以内の配達は保証できない．
- 受信機のHTTP接続タイムアウトは5秒．Web Pushのソケット無応答タイムアウトを2秒とし，最大1回の短い再試行を行う．DNSや接続確立に時間がかかる場合，受信機側が先にタイムアウトして再送する可能性がある．
- 送信先の受理までCloud Runのリクエストを開くため，その時間分の課金対象時間は増え得る．常時起動インスタンスや新しい有料サービスは追加していない．
- 受理時間は秘密情報や購読URLを含めずに件数と所要時間だけログへ出す．実配達の計測には端末側の受信時刻を別途集める必要がある．

- [RFC 8030](https://www.rfc-editor.org/rfc/rfc8030)のUrgencyとTTL．

- [Cloud Runのリクエスト課金とCPU割り当て](https://docs.cloud.google.com/run/docs/configuring/billing-settings)および[バックグラウンド処理の注意](https://docs.cloud.google.com/run/docs/tips/general)．
