# レイテンシー計測 v2 要件

## 目的

時計の異なる受信機，Cloud Run，ブラウザの時刻を差し引いた値を実測レイテンシーとして表示しない．各機器で測れる処理時間を再現可能な定義で記録し，未計測区間を明示する．

## 計測区間

| 項目 | 始点 | 終点 | 時計 |
| --- | --- | --- | --- |
| 受信機処理 | UBXフレーム抽出直後 | `decode_full`が返った直後 | Python `time.monotonic` |
| サーバー処理 | `/ingest`ハンドラー開始 | WebSocket `broadcast`直前 | Node `performance.now` |
| ブラウザ処理 | WebSocket `message`コールバック開始 | `renderReport`の同期処理終了 | Browser `performance.now` |
| 表示準備 | WebSocket `message`コールバック開始 | 描画要求後の2回目の`requestAnimationFrame` | Browser `performance.now` |

受信機処理には，シリアルポートで待った時間とフレーム抽出時間は入らない．サーバー処理には，HTTPの到達前とJSON解析の時間は入らない．表示準備は画素の実点灯を意味しない．非表示タブ，2秒以内にフレームが来ない場合，または次の通報が先に描画された場合は表示準備を欠測として記録する．

合計は「計測済み区間の合計」であり，受信機の送信キュー，端末からサーバーへの通信，サーバーからブラウザへの通信，OSの表示走査を含まない．したがって真のエンドツーエンド時間や通知到達時間とは呼ばない．

履歴は同じ電文について最初に届いたブラウザ報告だけを保存する．複数端末の分布を代表する値ではない．`p95`などの統計は保存済み電文の計測済み区間だけを表し，母数が少ない場合の性能保証には使わない．`/client-timing`は認証のない自己申告なので，公開値を監査済みの性能保証値として扱わない．

## 受け入れ条件

1. v2は全区間が非負の有限数である場合だけ保存する．表示準備がある場合はブラウザ処理以上である．
2. 受信機・サーバー・ブラウザが別の壁時計でも，区間の計算結果は変わらない．
3. ダッシュボードの統計・棒グラフ・履歴はv2のみを示し，旧方式の推定値と混ぜない．
4. 古い受信機のv1送信は取り込みを維持し，更新順序による通報の欠落を起こさない．
5. 異常値・欠測値・旧方式の表示混入を単体テストで検出する．ローカル結合テストで受信から履歴保存までを確認する．

## 将来の全経路計測

全経路時間が必要なら，受信機とサーバーの時刻同期誤差を実測し，ブラウザ側も同期またはRTTによる上下限を求める必要がある．時刻同期の状態だけを見て厳密な全経路時間と断定しない．
