# 地図・通報処理の最適化計測

計測日：2026年11月9日（月）．対象はブラウザ側の通報処理と独自地図エンジン．

## 変更内容

- GeoJSONの境界・本土範囲・中心座標を形状オブジェクトごとに保存し，同じ地理データの全頂点走査を繰り返さない．
- 気象区域のフィルターと色が変わらない場合，地図エンジンへの設定を再送しない．
- 独自エンジンの区域検索式を集合・索引で評価し，フィルター結果と各featureの表示色を，データ・式・ズームが同じ間だけ再利用する．変更時には再計算する．

## 再現方法

元版と改良版をそれぞれローカルサーバーで起動し，`BENCH_ORIGIN=http://127.0.0.1:<port> node scripts/benchmark-native-overlay.js`を実行する．macOSのChromeをヘッドレスで開き，CPUを4倍にスロットルする．静止中の重ね描き1600回，連続ズーム120フレーム，160区域を含む合成気象通報10回を測る．同じマシンで旧版・改良版を交互に3回ずつ実行した．数値はそれぞれの試行内の中央値の範囲．160区域の同時更新は高負荷時の挙動を見るための合成ケースであり，通常の衛星電文1件の所要時間を表すものではない．

| 指標 | 旧版 | 改良版 | 結果 |
| --- | ---: | ---: | ---: |
| 160区域を含む合成気象通報の再処理 | 3.6〜4.1ms | 1.9〜2.1ms | 約42〜54％短縮 |
| 160区域表示中の静止した重ね描き1回 | 1.024〜1.030ms | 0.113〜0.117ms | 約89％短縮 |
| ズーム中の重ね描き1回 | 1.026〜1.028ms | 1.024〜1.027ms | ほぼ同じ |

初回の通報，地図の初期表示，受信機からクラウドへの通信時間，プッシュ通知の配送時間は30％短縮を確認できていない．実際の全体レイテンシーが一律に30％短くなるという結果ではない．ラズパイ実機の計測も未実施．

## 表示の検証

ベンチマークでは旧版・改良版で，160区域の表示，その後の警報更新，フィルターと色の変更，GeoJSONソースの差し替えを行い，Canvas全画素のSHA-256が各段階で一致した．`BENCH_WEATHER_CODES=5`でも通常に近い少数区域の表示を比較した．

`npm test`は126件すべて成功．`node --check public/main.js`，`node --check public/native-map.js`，`git diff --check`も成功．

## 適用範囲

変更はWebとキオスクのブラウザ描画部分．衛星受信・デコード・サーバー側の通知経路は変更していない．独自描画の切り戻しには`?renderer=maplibre`を使えるが，地理計算キャッシュを含む全変更の切り戻しにはGitのコミットを戻す必要がある．
