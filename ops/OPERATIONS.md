## 復元

Macの復号鍵を失わないように別の安全な場所へ保管する．

```sh
openssl cms -decrypt -binary -inform DER -in state.cms -recip qzss-backup.crt -inkey qzss-backup.key -out state.tar.gz
mkdir recovered
# 復号内容はまず別ディレクトリで確認し，本番へ直接上書きしない．
tar -xzf state.tar.gz -C recovered
```

環境変数ファイルは600，格納ディレクトリは700とする．サービスの認証情報や復号鍵をログへ出力しない．

## YouTube配信画面の描画計測

配信ブラウザは各通報の計測結果をメモリ上の最大10件のリングに保持する．専用クラウドコンピュータの監視収集プログラムがloopbackのChrome DevTools Protocolから配信ページだけを読み取り，stream専用Bearerを付けた状態報告で送る．一般閲覧者の `/client-timing` はこの履歴へ入らない．認証されたstreamロールの値だけを `youtube-latency.json` へ別保存する．公開APIは `/api/youtube-latency-history`，公開情報の種別・時刻・震央名など必要な項目だけ返す．未計測はnullで維持し，ブラウザ処理時間を描画時間の代わりに使わない．二重rAFによる表示準備の指標であり，実点灯・ズーム完了・YouTube視聴遅延ではない．遡及計測はしない．

Oracle地図のCaddyブロックでは，このAPIだけを `127.0.0.1:8090` へ振り分け，その他は従来どおり `127.0.0.1:8080` へ送る．

```caddyfile
oracle-review.eq.shum10.com {
 handle /api/youtube-latency-history {
  reverse_proxy 127.0.0.1:8090
 }
 handle {
  reverse_proxy 127.0.0.1:8080
 }
}
```

監視サービス一覧は項目名と状態を行ごとに揃える．バックアップのinactiveは定期実行の待機中として扱い，失敗や未取得とは区別する．配信クラウドの作業は録画中・投稿中・投稿待ち・概要欄更新中／更新待ちを併記し，保存されている失敗ジョブまたは概要欄更新失敗があれば要確認とする．


## 現在の災害情報と基盤機能

配信サーバーの収集プログラムは，同じCDP読み取りで `activeEvents` と `displayStore` の期限・受信時刻・パネル用の見出しと要約を取得する．描画対象の選択はViewCycleの複製を使い，地図本体の巡回状態を変更しない．最大20件・要約8行に制限し，HTMLは転送・実行しない．未完了の初期読み込みや取得失敗を空の正常状態として扱わない．監視サーバーはstream専用認証で受けた状態だけをdisplay-state.jsonへ保存する．

管理画面は，最新の確認で空なら待機中，60秒を超えて確認できなければ要確認とする．残り時間はブラウザが報告した期限までの差を収集側の時刻へ合わせ，単調時計で秒表示する．期限に達しても，次のスナップショットで削除を確認するまでは消去確認待ちと表示する．レイテンシーは同じrawキーと試験区分・受信時刻帯が一致した配信ブラウザの計測だけを紐付ける．録画マークは配信画面全体のジョブ状態を示し，特定の災害情報だけが録画される保証はしない．

上部カードの主要機能には，基盤サーバーの通報受信・通知設定とAPI応答・地図設定API・配信ブラウザの描画確認・定期検査の実行結果・障害監視・バックアップを表示する．通知の実配送は自動試験しない．配信サーバーではライブ進捗・録画投稿・最新の画面監視・systemdの再起動設定・バックアップ結果を表示する．強制障害や復旧試験は行わず，設定と直近結果の確認として区別する．systemdの実行結果は60秒ごとに読み取り，3分を超えた情報から正常を断定しない．

処理端末の消費電力・追加ウォッチドッグ調査は利用者の指示で後続作業とし，今回の配備では処理端末へ変更しない．


## 処理端末のウォッチドッグと接続表示

Raspberry Pi 3B+では，受信プログラムのRestart=on-failure，受信監視タイマーと最終正常終了，受信監視ファイルの更新，OSのRuntimeWatchdogUSecとsysfsのwatchdog0のstate・timeout・timeleftを個別に確認する．受信アプリ自身のWatchdogUSecが0でも，別系統の受信監視とOS側の監視の有効性はそれぞれで評価する．/dev/watchdogを開いて調べることはせず，sysfsの読み取りだけを行う．再起動や強制障害による試験はしない．

構成・systemdの確認は60秒ごと，ハードウェア監視の状態と残りカウントは状態収集ごとに取得する．収集が古い，監視カウントが未取得・停止，設定無効の場合は要確認とし，未確認を正常にしない．詳細には監視期限・確認時点の残りカウント・監視実行の最終完了時刻を表示する．

ネットワークの通常表示はWi-Fi／有線LAN，最終応答の経過時間，接続状態，電波の目安へ整理する．wlan0やup，正確な応答時刻は同一URLの詳細画面へ移す．Wi-Fiの強弱は-60 dBm以上を強い，-70 dBm以上を中程度，それ以下を弱いとする表示上の目安であり，通信速度やインターネット到達性を保証しない．


## 公開閲覧と管理操作

status.shum10.comでは監視画面と必要な読取API・静的アセットだけを認証なしで公開する．公開APIはYouTubeの下書き・編集指示本文・CSRF・概要欄編集用ハッシュ・OS起動UUIDなどを返さない．管理は/manage/youtubeへ遷移したときに既存のBasic認証を要求し，編集APIの認証・Origin・CSRF・版番号検査を維持する．replay.shum10.comや保存電文APIは従来どおり認証対象とし，書き込みの認証をGETの公開許可と混同しない．

稼働時間はJSTの起動時刻から満年・満月を暦で計算し，端数の日・時間を付ける．月末は移動先の月末へ丸める．満1年になるまで年を出さず，0の単位も出さない．1時間未満は「1時間未満」．OSの稼働時間とYouTubeの配信継続時間に同じ書式を使う．停止時間の集計と応答の何秒前表示は別の指標として維持する．

### サーバー処理時間の計測

`/api/server-latency-history` はOracleのWebSocket受信から保存する．`schema_version: 2` の受信機とサーバーそれぞれの単調時計による区間を合算する．サーバー区間は `/ingest` の認証前からWebSocket配信直前までであり，通知配送完了までではない．通信・JSON本文の受付以前・ブラウザ描画時間は含まない．時計差を使った片道通信時間の推定はしない．再接続時の復元情報は再計測しない．過去の配信ブラウザ記録を引き継ぐ場合は処理区間だけを採用し，収集元を明示する．

OracleのCaddyは `/latency.html` と `/api/server-latency-history` を8090へ振り分ける．地図本体のコンテナと配信エンコーダを再起動せず監視画面を更新できる．

### 基盤サーバーの常時待機（v1.23.1）

通知は既存の常駐Nodeプロセスで受信時に即時送信を開始する．ゼロ台への縮退やアイドル停止は使わない．Dockerはunless-stopped，docker.serviceは自動起動．CPU競合時の相対優先度は基盤サーバー2048，監視コンテナ256のCPU sharesとする．CPUの占有や通知到達時間を保証する設定ではない．バックアップ等は低いNiceを維持する．

`foundation-standby.py` を `/opt/qzss-ops/`，同名service/timerをsystemdへ配備する．15秒ごとにローカルの設定API・通知設定APIを確認．応答失敗が3回連続した場合に既存コンテナを再起動する．再起動は最低5分空ける．通知無効という設定自体では再起動せず，明示的に停止したコンテナも起動しない．結果は `/var/lib/qzss-standby/state.json` とjournalに記録する．監視は通知送信や擬似電文の投入を行わず，実配送成功を証明しない．これは単一VM上の常駐待機であり，別VMへの自動フェイルオーバーではない．

再配備後は `docker update --cpu-shares 2048 qzss-server-review` と `docker update --cpu-shares 256 qzss-ops` を適用する．

### 配信の軽量化とフレーム品質（v1.24.0）

時計監視はffmpeg.progressの最後の16KiB以内・最後の完結レコードだけを読む．進捗ログの全文を取り込まない．配備時はqzss-clock-watchだけを再起動し，qzss-streamとqzss-clipsは止めない．収集エージェントのfps区間は，CDP応答待ちの前ではなくフレームを読む時点の単調時計を使用する．

ダッシュボードは直近約1分（実際の区間秒数を併記）の破棄・重複と，1分換算での前区間比較を表示する．30分の推移グラフも同じ計算．90秒を超える観測間隔，カウンタ減少，エンコーダ再起動を検出した区間は収集中とする．出力fpsには同じ映像による補完も含む．累積破棄数は減らないため補足とする．

`/home/ubuntu/qzss-stream/recovery-test.json` は運用者の実試験結果．公開するのは時刻と6個の真偽値のみ．画面プロセスを終了して再起動・画面正常化，配信サービスとFFmpegのPID維持・フレーム進捗を確認する．systemdは隔離した短命サービスの異常終了からの自動再起動を確認する．これは実配信のエンコーダ・Xvfb・VM全体の障害試験ではない．試験記録がすべて成功の場合のみ，復旧説明を試験済みの範囲へ変更する．処理端末の再起動・OSウォッチドッグ試験の表記は変更しない．

### GCP比較接続の停止（v1.24.2）

費用削減のため，GCPへの比較用WebSocketは既定で接続しない．`OPS_CAPTURE_GCP=true` を明示した場合だけ再開する．Oracleの記録・監視・通知・YouTube配信は継続する．比較停止中は片系統欠落の検査を行わず，再生画面に停止中と表示する．GCP側の地図を閲覧する別クライアントがWebSocketを維持した場合は，Cloud Runの稼働課金が残る．本番URL・処理端末の送信先はこの変更では変えない．

### 常時解析と通信品質（v1.25.0）

`qzss-analysis.service` は別Pythonプロセスで保存済みOracle電文のJSONLを5秒ごとに差分読取りする．初回は直近2ファイルそれぞれ末尾2MiB以内から開始し，1ファイルにつき最大100行ずつ処理する．カーソルと照合済みキーを保存し，再起動時の二重集計を抑える．rawのある送信済み電文のみが対象で，処理端末がサーバーへ送らない電文は検査できない．手動テスト電文は除外，公式訓練は検査対象に含む．

azarashi 0.16.4の別実行で全復号項目を比較する．取込時刻・NMEAの大文字小文字・表示用付加情報・内部camf表現・DCXの現在週から導出する日時は比較対象外．DCXの週・時刻の元フィールドは比較する．同じライブラリの共通欠陥を独立検出する実装ではない．結果は一致／不一致／復号エラー／生電文なし．1日・同一内容の繰返しは照合済み1000件の範囲で除く．復号結果はRAMに256件までキャッシュ．生電文を新たに外部へ送らない．

通信品質はOracleの実Heartbeatのみを対象としReceiverStatusは除外．30分の中央値・P95・30秒周期からの平均絶対偏差・45秒を超えた区間数・推定欠落を算出．monitor.jsonに記録した監視WebSocket停止区間を除外する．これは到着間隔による推定であり，端末・回線・サーバーのどの段階で失われたかは特定しない．公開JSONに電文・認証・カーソルを含めない．検査結果100件・照合済み1000件・ハートビート24時間，日別集計7日を上限とする．

配備：/opt/qzss-analysis/venvにanalysis-requirements.txtの依存を入れ，analysis_worker.pyを配置．/var/lib/qzss-ops/analysisをroot700で作成後，qzss-analysis.serviceを有効化する．Nice19，CPUQuota10%，MemoryMax96M，ネットワークアクセス禁止で通知エンジンと隔離する．通知エンジンの動作・購読・送信先を変更しない．

### 回収防止処理と状態表示（v1.25.3）

ユーザー指定により，基盤サーバーだけに `tools/oci-background-compute/` の低優先度計算サービスを追加．回収判定や回収防止を保証する機能ではない．独立したSCHED_IDLE・CPU上限・メモリ上限付きの数値積分を行い，本来の処理のCPU20%以上・steal30%以上・空きメモリ192MiB未満・既存の受信通知監視がready以外または60秒より古い場合に休止，正常が15秒続けば再開する．しきい値と操作方法は同ディレクトリのREADMEを参照．

状態JSONは数字と許可した状態名だけを公開可能な権限で保存し，既存の非特権監視収集からトップレベルのbackgroundComputeへ渡す．稼働状況サイトの基盤サーバー機能一覧・詳細に動作中／停止中／要確認と休止理由を表示する．監視データが古い場合は動作中と表示しない．配信サーバーや処理端末にはこの計算を配置しない．

実機で計算結果の照合とCPU・メモリ制限の適用を確認．隔離した一時サービスで5秒間のCPU制限付き負荷を与え，通常処理CPU約25%でforeground-cpuへ移ることを確認した．本番の受信・通知プロセスを強制停止する試験は行っていない．

### 計算量の調整と停止条件の公開（v1.25.6）

回収防止処理を2並列・CPU使用率30%目標の実測フィードバック制御に変更．低優先度とメモリ64MiBを維持し，合計CPUQuota100%（論理CPU1個分）を上限とする．cgroupのCPU計上とカーネルnice時間を照合し，CPU待ちの計上差で通常処理の負荷を引きすぎないよう補正する．

通常処理CPU25%以上が3秒継続，steal70%以上が10秒継続で休止．通常処理CPU60%以上，空きメモリ192MiB未満，受信・通知の監視異常／60秒超の未更新，手動休止は即休止．正常5秒で再開．短時間のCPU待ちでは計算量を調整して続行する．

管理画面の基盤サーバー詳細で，目標CPU・実測CPU・直近の停止時刻・理由・停止判定時のCPU/steal/空きメモリと，別詳細ビューの停止・再開条件を公開する．再開後も直近の停止記録を残す．秘密のパスや自由文はメトリクスへ含めない．

実機の短時間検証では無停止で継続したが，CPU実測は約25%で頭打ち．30%の常時維持は未達であり，表示を30%へ固定したりOracleの回収防止を保証したりしない．負荷試験の実測が停止しきい値に届かなかったケースを，停止試験成功として扱わない．手動休止・再開と停止記録の保持を実機・公開APIで確認済み．一時的にCPUQuotaを150%へ広げた20秒の試験でも実測平均24.97%だったため，終了後に100%へ戻した．
